## Reasons

### Requirements stability

- Waterfall: Even though our requirements are mostly settled, any unexpected changes would force us to redo earlier stages, making a rigid plan a poor fit.
- Incremental: We can build on some core features first, so later when we want to add on, it is easier to do it.
- Scrum-style: we have stable requirements, so it makes sprint planning straighforward

### Client availability

- Waterfall: TThe client can approve early plans, though they only review working features near the end.
- Incremental: We can get client feedback as soon as each working piece is finished.
- Scrum-style: regularly reviews by client, will help us on keeping track with the project.

### Team experience

- Waterfall: Linear plan might look good, but when we have trouble for days, we might feel frustrated.
- Incremental: We divide tasks well and so our team collaborate and deliver the work well
- Scrum-style: We can manage work cycle but we need a better discipline.

### Deadline (week 14)

- Waterfall: If there is something change happend immediatly, we might have trouble with the deadline.
- Incremental: Finish work one piece at a time and show it to client for feedback before moving on.
- Scrum-style: Regular sprint deadlines keep us moving, though managing constant adjustments under a strict 14-week limit adds extra pressure

### Risk

- Waterfall: An immediate change in plan would force us to redo earlier stages, making a rigid upfront schedule risky.
- Incremental: Testing each completed piece catches bugs early on, though we still risk integration issues when connecting separate features together.
- Scrum-style: An immediate change in plan is caught and managed quickly through regular sprint reviews, keeping overall project risk low.
