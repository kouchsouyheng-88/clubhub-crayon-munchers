# Failure Risks · ITC Club Hub (v0.1, 2026-10-20)

| # | How the project could fail | Chapter 01 topic | Early warning sign | First countermeasure | Owner |
|---|----------------------------|------------------|--------------------|----------------------|-------|
| F1 | The business rules (capacity, no double registration, 24 h cancellation, no past events, approved clubs only) interact in ways nobody sees, so the Sprint 1 demo shows contradictory behaviour and the team cannot explain where a rule is enforced | Topic 3 - Essential difficulties (complexity, invisibility) | Two members give different answers to "what happens if a student cancels for a full event?"; nobody can point to the file where a rule lives | Number every rule in the README; one function and one unit test per rule; draw the rules in a model before coding (Chapter 06) | Ung Phearakleap |
| F2 | The team of 5 plus the client has 15 communication paths; decisions get lost, two members build the same thing, and a sixth member added in week 11 makes Sprint 2 later, not faster | Topic 4 - Scale and communication | Someone says "I did not know that was decided"; two pull requests change the same rule | Only the Product Owner talks to the client (11 paths); GitHub Issues as the single work list; decisions in lab01/decisions.md; no new member late, cut scope instead | Kouch Souyheng  |
| F3 | A rule is misunderstood (for example "cancel up to 24 h before" built as 2 h) and found only after the Sprint 1 demo, so fixing it costs many times more than in a review | Topic 5 - Changing requirements and the cost-of-change curve | The client says "that is not what I meant" in the demo; a rule has no written acceptance criteria | Confirm every business rule with the client in writing before coding it; write acceptance criteria per rule; handle later requests as change requests with an impact analysis | Buntong Anupheap |
| F4 | The final demo fails live because the program crashes or shows wrong seat numbers when the client loads a hand-edited CSV with a bad value (such as "abc" or "-5" as capacity) | Topic 6 - Reliability, security and safety | Program crashes or prints negative seats on a edited file; file input is read with stoi or atoi | Validate every field with std::from_chars into std::optional; accept capacity only from 1 to 500; skip and log bad rows; test with bad files; run the demo from a clean clone before presenting | Ou Pechly |
| F5 | Quick fixes under deadline (copy-pasted checks, missing tests) pile up, so in Sprint 2 every change takes longer and the team misses the deadline | Topic 7 - Legacy, integration and technical debt | The same check appears in two places; a small change needs edits in many files; the build breaks after a rule change | One validation function per rule; record each shortcut as a GitHub issue labelled tech-debt with principal and interest; repay one item each sprint | Yam Soksopheakna |
